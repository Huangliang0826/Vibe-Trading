# Alpha Mind 健康与智能控制台设计

## 目标

为 Alpha Mind 增加一个本地优先、趋势优先的数据洞察系统，帮助维护者每天回答四个问题：

1. 哪些功能真正被使用并产生了有效结果？
2. 哪些接口、数据源或任务变慢、失败或不稳定？
3. Scanner、Forecast、Backtest 和 Paper Trading 的研究质量是否持续有效？
4. 最近增加了哪些 feature，代码和版本变化之后，产品指标发生了什么变化？

第一版服务个人本地使用，但所有事件预留 `workspace_id` 和匿名 `user_id`，未来支持多用户时无需重建数据模型。Dashboard 以异常和趋势为中心，而不是仅展示累计数字。

## 产品原则

- **异常优先**：首页首先展示需要处理的变化、影响范围和下钻入口。
- **趋势优先**：核心数字必须有 7、30、90 天趋势，可与上一周期比较。
- **可解释**：胜率、收益和健康度同时展示样本量、基线和不确定性。
- **相关性不冒充因果**：版本标记用于对照发布前后变化，不自动断言某个 commit 导致变化。
- **业务路径优先**：分析采集失败不得阻塞行情、扫描、预测、回测、Agent 或交易路径。
- **隐私默认保护**：不采集提示词、API Key、完整模型响应、账户凭据或未列入白名单的业务载荷。

## 已选择的方案

采用“健康与智能控制台”方案，将产品使用、系统健康、研究质量和研发版本统一在一个分析层中。纯产品埋点无法表达量化研究价值；纯模型质量实验室又无法发现功能弃用、失败和性能问题。统一控制台能把“做了什么、运行得怎样、结果是否可靠、在哪个版本后变化”串成一条时间线。

## 页面与信息架构

新增侧边栏入口“数据洞察”，路由为 `/analytics`。页面包含一个总览和四个下钻视角。

### 总览

- 时间范围：7、30、90 天，默认 30 天。
- 对比：默认开启上一等长周期对比。
- 顶部卡片：综合健康分、有效研究会话、任务成功率、Forecast 方向准确率；每张卡包含迷你趋势、变化值和样本量。
- 主趋势图：在“功能使用、系统健康、研究质量、研发动态”四组指标间切换。
- 时间轴标记：commit、tag 和应用版本；点击标记进入研发与版本视角。
- 异常队列：按严重度、持续时间、影响样本和最近变化排序。
- 最近开发与版本：用户可读 feature、commit、影响模块、变更规模和测试变化。

主趋势图默认不混用不同单位的双 Y 轴。跨单位比较使用标准化趋势视图；绝对值视图将不同单位拆成小图。原始值、EWMA、基线和置信区间可以独立开关。

### 功能使用

- 页面和核心操作的启动次数、完成率、结果查看率、失败率。
- 有效研究会话数和占比。
- Time to Insight：会话开始到首次查看有效研究结果的耗时。
- 核心路径：总览 → Scanner/Forecast → Backtest/Paper Trading → 保存或比较实验。
- 长期无人使用、使用下降或“任务完成后未查看结果”的功能。
- 按功能、版本和匿名用户下钻；单用户模式默认不展示无意义的用户分组。

“有效研究会话”指一个会话中至少有一个 Scanner、Forecast、Backtest、Paper Trading 或 Research Analysis 任务成功完成，并且用户查看了结果。仅打开页面或发起后失败的任务不计入。

### 系统健康

- API、Agent tool、后台任务和外部数据源的成功率。
- P50、P95 耗时，超时数和机器可读错误类型。
- 行情数据的新鲜度、完整率和缺失观测。
- 按 operation、provider、市场、功能和版本下钻。
- 缓存命中率只在已有可靠缓存语义的路径中展示，不为了 Dashboard 改造无关缓存。

### 研究质量

- Scanner：1、5、10、20 日胜率、平均前瞻收益、排名分层收益、top-minus-bottom spread 和置信区间。
- Forecast：方向准确率、MAE、预测区间覆盖率、校准度和样本量。
- Backtest：总收益、Sharpe、最大亏损、最大回撤和样本外表现。
- Paper Trading：同配置回测与模拟盘的收益、风险和成交差异。
- 滚动窗口：按市场、预测周期和 market regime 观察模型或策略衰减。

后验验证沿用现有 Scanner、Forecast、Backtest 和 Paper Trading 的权威计算结果。分析层只读取并聚合，不重新实现财务指标公式。

### 研发与版本

- 从本地 Git 读取最近 commit、tag、日期、作者、标题和变更统计。
- 将相邻、主题一致的 commit 合并成用户可读 feature；第一版将 24 小时内、至少触及一个相同功能模块且标题关键词有交集的连续 commit 归为一组，否则保留为单独 feature。每组始终保留原始 commit 列表，不调用外部 LLM。
- 展示影响文件、模块、增删行、测试文件变化和高频修改模块。
- 代码增删行仅表示变更规模，不参与综合健康分，也不代表代码质量。
- `frontend/package.json` 是应用版本的唯一来源；构建时将该版本同时暴露给前端和后端，替换 Layout 中独立维护的硬编码版本。匹配 `v*` 的 Git tag 定义正式发布边界；没有 tag 的 commit 只显示为开发变更，不伪装成 release。
- 版本影响视图比较发布前后等长周期的功能使用、错误率、P95、数据质量和研究质量，默认窗口为发布前后各 7 天，可切换为各 30 天。
- 发布前后对比必须展示样本量，并标注为时间相关性分析。

## 数据架构

### 模块边界

后端新增独立的 `src.analytics` 包，职责拆分如下：

- `models`：事件、查询和聚合结果的数据契约。
- `collector`：字段白名单、校验、去重和批量入队。
- `store`：独立 SQLite 的事务、迁移、查询和保留策略。
- `rollup`：小时、日和版本粒度的幂等聚合。
- `statistics`：趋势、区间、基线和异常判断。
- `git_activity`：只读解析 Git 历史并产生开发事件。
- `service`：组合存储、统计和 API 所需的视图模型。

前端新增独立 `Analytics` 页面和按视角拆分的组件。页面只负责筛选、格式化和渲染，不在浏览器重新计算研究质量或健康分。

### 存储

分析数据写入运行时数据目录中的独立 `analytics.db`，不混入现有业务数据库。SQLite 使用 WAL；所有 schema 变更使用单调递增的迁移版本。

四类追加事件：

1. `product_event`
   - `event_id`, `occurred_at`, `workspace_id`, `user_id`, `session_id`
   - `feature`, `action`, `outcome`, `duration_ms`
   - `app_version`, `commit_sha`, `metadata`
2. `system_event`
   - 通用身份字段
   - `operation`, `provider`, `market`, `status`, `duration_ms`
   - `error_code`, `data_freshness_ms`, `sample_count`, `metadata`
3. `quality_observation`
   - 通用身份字段
   - `subject_type`, `subject_id`, `market`, `horizon`, `regime`
   - `metric_name`, `metric_value`, `sample_count`, `formula_version`, `as_of`
4. `development_event`
   - `commit_sha`, `occurred_at`, `version`, `summary`
   - `files_changed`, `insertions`, `deletions`, `modules`, `test_files_changed`

`metadata` 只接受按事件类型注册的字段，未知字段被拒绝而不是盲目存储。所有事件通过 `event_id` 去重。

日级聚合表保存维度、指标、值、分子、分母、样本量、区间上下界、数据截至时间和计算版本。比例指标必须保留分子、分母，不能只保存百分比。

### 采集

- 前端对明确命名的功能动作埋点，短时间内批量发送。
- FastAPI 中间件记录 API 状态与耗时；业务 service 在比 HTTP 更合适的位置记录 provider、tool 和后台任务结果。
- 研究质量适配器从现有权威结果读取观测。
- Git 活动在 Dashboard 请求或定时聚合时增量扫描本地仓库，不访问网络。
- 当前个人模式使用固定的 `workspace_id=local` 和不可逆生成的本地匿名 `user_id`。

采集进入有界内存队列并批量写入。队列满、数据库忙或 schema 校验失败时增加内部丢弃计数并记录不含载荷的诊断日志，不阻塞业务请求。正常关闭时尝试在有限时间内刷新队列。

Rollup 在应用启动时补算缺失日期，之后每小时执行一次小时聚合，并在本地日期跨日后生成前一日的最终日聚合。重复执行使用相同幂等键覆盖，不追加重复行。

## API 设计

- `POST /api/analytics/events`：接收前端白名单事件批次。
- `GET /api/analytics/overview`：健康卡片、异常队列、主趋势和版本摘要。
- `GET /api/analytics/trends`：按指标、时间范围、粒度和维度返回时间序列。
- `GET /api/analytics/usage`：功能使用、有效会话和路径漏斗。
- `GET /api/analytics/system-health`：operation/provider 的成功率、耗时和数据质量。
- `GET /api/analytics/research-quality`：现有研究结果的滚动聚合和区间。
- `GET /api/analytics/development`：commit、feature 分组、变更规模和版本影响。

所有路由沿用现有本地或认证访问策略。所有查询响应包含 `data_through`, `generated_at`, `sample_count`, `calculation_version` 和 warnings。不可用值返回 `null` 和原因码，不能用零替代。

## 统计方法

### 趋势

- 原始日值作为可验证基础。
- 7 日移动中位数抵抗单日极端值。
- EWMA 提供平滑方向，默认 `alpha=0.3`。
- 上一周期变化同时报告绝对变化和相对变化；比例指标使用百分点变化。
- 少于 3 个有效日时不绘制趋势结论。

### 不确定性

- 成功率、胜率和方向准确率使用 95% Wilson 区间。
- 平均前瞻收益和策略差异使用固定随机种子的 percentile bootstrap 95% 区间，默认 2,000 次重采样。
- Dashboard 必须在 tooltip 或明细中显示样本量和区间。

### 异常

- 对至少 7 个历史日的序列使用 median/MAD 稳健 Z-score。
- `|robust_z| >= 3.5` 视为候选异常。
- 候选异常必须连续两个聚合周期，或单周期进入显式 critical 阈值，才进入异常队列。
- 比例指标至少 20 个样本；收益和质量指标沿用其现有最低样本规则，若现有规则更严格则采用更严格者。
- 规则、阈值和计算版本可配置并在明细中可见。

第一版不做机器学习异常检测。后续只有在积累足够历史数据并验证误报率后，才考虑变化点检测或季节性模型。

### 综合健康分

综合健康分为 0–100 的可解释摘要，由四个维度组成：

- 功能有效性：25%
- 系统可靠性：25%
- 数据质量：20%
- 研究质量：30%

每个底层指标先依据显式规则得到 `healthy=100`、`watch=65`、`critical=25`；不可用指标从加权分母中排除。可用权重不足 50% 时综合分返回不可用。研发活跃度和代码量不计入健康分。页面提供“分数如何计算”的下钻，并将该分数标为实验性，直到至少积累 30 天数据。

## 异常与错误处理

- 分析采集、Git 读取或聚合失败不改变业务请求结果。
- 聚合任务以日期、维度和计算版本为幂等键，可安全重跑。
- 原始事件断档显示为缺失，不补零、不跨断档插值。
- Dashboard 查询失败时可返回最后一次成功聚合，但必须标记缓存时间和 stale warning。
- 版本对比任一侧样本不足时不计算变化结论。
- Git 不可用或工作目录不是仓库时，研发视角显示明确空状态，其他视角继续工作。
- 所有数据库写入使用事务；失败批次整体回滚。

## 保留与隐私

- 原始 product/system 事件保留 90 天。
- 原始 quality/development 事件长期保留，因为它们用于历史验证和版本对照。
- 小时聚合保留 180 天；日级和版本级聚合长期保留。
- 每日聚合完成后执行有界清理，不在业务请求中进行大规模删除。
- 不记录 prompt、response、API Key、OAuth token、订单凭据或完整请求体。
- symbol、strategy 名称等研究维度仅在相应白名单事件中保存；未来多用户模式允许 workspace 级禁用或哈希处理。

## MVP 范围

第一版交付：

- `/analytics` 页面及五个视角。
- 四类事件契约、独立 SQLite、批量采集和日级聚合。
- 7/30/90 天趋势和上一周期比较。
- 可解释的基线、区间和异常队列。
- 本地 Git commit、feature 分组、代码变更和版本标记。
- 现有 Scanner、Forecast、Backtest 和 Paper Trading 质量数据接入。

第一版不包含：

- 多用户账户、权限或跨 workspace 管理。
- 第三方 SaaS 埋点或远程 telemetry。
- 自定义拖拽 Dashboard。
- 机器学习异常检测、自动因果归因或 LLM 自动发布说明。
- 对现有研究指标公式的重写。
- tick 级实时分析仓库。

## 测试

### 单元测试

- 事件白名单、去重、迁移和保留策略。
- 移动中位数、EWMA、MAD、Wilson 和 bootstrap。
- 健康分的权重、缺失值和不足 50% 可用权重行为。
- commit 模块映射、feature 分组和版本窗口。

### 集成测试

- 事件 → 队列 → SQLite → 日聚合 → API 完整链路。
- Scanner/Forecast/Backtest/Paper Trading 权威结果 → quality observation。
- 采集失败、队列满、数据库锁和聚合重跑不影响业务路径。
- 90 天原始事件清理保留正确聚合。

### 前端测试

- 正常趋势、空数据、小样本、断档、stale 数据和 API 失败状态。
- 7/30/90 天、上一周期和视角切换。
- 版本标记、tooltip 样本量和异常下钻。
- 响应式与深浅色表现。

### 性能与隐私测试

- 对代表性 API 测量启用分析前后的 P95；采集不得造成超过 5% 的相对回退。
- Dashboard 30 天默认查询在本地开发数据规模下应在 500 ms 内完成。
- 自动扫描分析数据库和诊断日志，禁止出现凭据、prompt 或完整模型响应。

## 验收标准

1. 连续采集 7 天后，功能使用、系统健康、研究质量和研发动态均有可追溯趋势。
2. 每个比例和质量指标都能下钻到样本量、时间范围、计算版本和数据来源。
3. 合成数据能够稳定触发一种性能异常和一种研究质量下降；正常噪声不触发相同告警。
4. Git 时间轴展示真实 commit、模块和变更规模，发布前后指标明确标注为相关性。
5. 分析数据库不可用时，现有核心业务测试和功能行为保持不变。
6. 不可用或样本不足的指标显示原因，不显示伪造的零值或确定性结论。
7. 前后端测试、生产构建、性能回退预算和敏感数据扫描全部通过。

## 分阶段实施建议

1. 数据基础：事件契约、SQLite、collector、rollup 和查询骨架。
2. 系统与产品：前端行为、FastAPI 性能、数据源健康和基础趋势。
3. 研究质量：接入现有质量结果、区间、滚动窗口和异常。
4. 研发版本：Git 活动、feature 分组、版本标记和发布前后对比。
5. Dashboard：总览、四个下钻视角、空状态和响应式验证。

每一阶段都可以独立测试和启用。分析模块由单一配置 `ANALYTICS_ENABLED` 控制，本地版本默认开启；关闭后不注册前端采集，也不启动后端聚合任务。该开关只控制本地分析，不产生任何外部网络传输。
